Both cards below are locally authored extensions. They are not represented as benchmark-native questions. Scientific provenance and the boundary of deterministic checks are documented in `docs/research/ls09-local-extension-provenance.md`.

## `ls09-opentrons-sop`

> **READY / schedulable.** Codex C0 trial-2 exposed an ambiguous transfer-plan granularity and missing simulator. The plan is now fixed at 192 net-transfer rows, Opentrons 7.1.0/API 2.16 is pre-provisioned for both conditions, the reference protocol simulates successfully in 3/3 clean runs, and the accepted oracle rejects wrong, empty and legacy-tip controls. The host-platform deviation is recorded in the campaign release status.

- **Domain / sub-domain:** life_science / experimental automation and research data
- **Level / time:** L2 / 45 minutes
- **Anchor / related:** X / D,P,A,O
- **Source idea:** Opentrons official Python Protocol API tutorial, instrument API, Magnetic Module API, and labware-definition documentation; local frozen fixture.
- **Inputs:** `sop.md` states the biological workflow; `labware.csv` freezes deck/module/labware; `instrument.csv` freezes robot, API, pipette, and tips; `sample_map.csv` freezes the 24 preloaded sample wells; `reagent_map.csv` freezes reagent locations, starting volumes, and dead volumes; `simulator_contract.json` freezes the supported platform, dependency lock, invocation, and success criteria; `README.md` documents schemas, units, provenance, and the remaining acceptance boundary.
- **Prompt:**

  > Read every file under `inputs/`. Translate the frozen 24-sample magnetic-bead cleanup SOP into an auditable OT-2 Opentrons protocol. Use no external data and do not alter inputs. Write `output/protocol.py`, `output/transfer_plan.csv` with exactly the columns `step,source,destination,volume_uL,pipette,tip_policy`, `output/simulation.txt`, and `output/report.md`. `transfer_plan.csv` is a net liquid-transfer stage table, not a command log: write exactly one row per SOP net-transfer stage per sample (`lysis`, `beads`, `supernatant`, `wash1_add`, `wash1_remove`, `wash2_add`, `wash2_remove`, `elution`), for 8 × 24 = 192 rows. Do not add one row per mix stroke, aspirate command, dispense command, delay, magnet action, or tip action; represent those operations in `protocol.py` and summarize them in `report.md`. Identify each row as `<stage>:<well>` and use the frozen role/well identifiers. Respect the declared deck, Magnetic Module compatibility, API level, pipette range, well capacity, reagent dead volumes, liquid balance, and tip policy. Run the evaluator-pinned simulator using the supplied invocation and record its unedited outcome in `simulation.txt`; if that simulator or invocation is unavailable, record the failure and abort rather than claiming success.

- **Deliverables:** four fixed paths in the Prompt; UTF-8 text; parseable CSV; finite microlitre values.
- **Hard gates:** exactly 24 samples and exactly the eight defined net liquid-transfer stages per sample; mix strokes and low-level commands excluded from the plan; declared sources/destinations only; correct volumes and mass balance; 20–300 uL instrument range; the frozen six-tip-per-sample contamination policy (144 tips total, supplied by two 96-tip racks); static Opentrons contract and genuinely executed pinned-simulator success. Simulator absence must produce an honest abort, not a scientific failure, but the run cannot pass this hard gate.
- **Deterministic 80:** coverage 10; exact transfer contract 16, balance/well mapping 12, pipette 6, stage-specific contamination-safe tip lifecycle 6; protocol decision 8 and validation record 7; summary 5; parseable `protocol.py` 10. Details are executable in `docs/oracles/ls09-opentrons-sop/scientific_checks.py`. The acceptance suite contains a deliberate 72-tip legacy control that must fail.
- **Judge 20:** clarity of audit trail, explanation of magnetic-bead handling risks, limitation that static validation is not hardware verification, and readability.
- **Ablation:** expose only experiment-approved catalogue capabilities; the agent autonomously discovers/installs/calls any needed subset. Clear installed capabilities after each run.

## `ls09-plate-dilution-recovery`

- **Domain / sub-domain:** life_science / experimental automation and research data
- **Level / time:** L2 / 40 minutes
- **Anchor / related:** A / D,P,X,O
- **Source idea:** conservation-of-solute dilution equation, frozen pipette constraints, and Opentrons official dilution tutorial; local frozen fixture.
- **Inputs:** `dilution_request.csv` freezes requested concentrations/replicates; `plate_map.csv` maps every requested well; `run_log.csv` freezes completed and failed-before-aspirate events; `source_inventory.csv` freezes intermediate sources and available volumes; `pipettes.csv` freezes usable ranges.
- **Prompt:**

  > Read every file under `inputs/`. Diagnose the stopped dilution run and generate only the recovery work that remains physically necessary. Use no external data and do not alter inputs. Write `output/root_cause.json` with `failed_well,failure_mode,liquid_moved,completed_wells,recovery_wells`; `failure_mode` may be a concise controlled phrase that states the failed operation and whether it occurred before aspiration. Write `output/recovery_plan.csv` with exactly `step,source,destination,transfer_uL,transfer_pipette,diluent_source,diluent_uL,diluent_pipette,final_concentration,final_volume_uL`; the two pipette fields identify the physical instrument for each distinct liquid movement. Also write rerunnable `output/analysis.py` and `output/report.md`. Enforce the plate map, event ordering, `C_source*V_transfer=C_final*V_final`, source inventory, solvent identity, and frozen pipette ranges. Do not redo completed wells. Abort explicitly rather than inventing a missing transfer.

- **Deliverables:** four fixed paths; parseable CSV/JSON; concentrations in uM and volumes in uL.
- **Hard gates:** root cause semantically traceable to log under the controlled failure vocabulary; only unfinished wells recovered; dilution and volume balance correct; transfer and diluent operations each name their own feasible pipette; no source overdraw; script rerunnable.
- **Deterministic 80:** coverage 10; root cause 14, recovery scope 10, dilution balance 10, pipette/inventory 6; recover decision 15; summary 5; script 10. Details are executable in `docs/oracles/ls09-plate-dilution-recovery/scientific_checks.py`.
- **Judge 20:** clarity, separation of observed log facts from calculation, operational error-recovery explanation, and readability.
- **Ablation:** expose only experiment-approved catalogue capabilities; the agent autonomously discovers/installs/calls any needed subset. Clear installed capabilities after each run.
